## 二、必须记住的 4 条判断

1. **起点是语料，不是"文档入 RAG"**——第 1 环是「从哪来、怎么拿到」，不是「已经有了」。
2. **编码与索引是两件事**——编码：文本→向量（丢字面形态）；索引：向量→ANN 结构（丢精确召回）。合并成一步就说不清信息在哪丢。
3. **检索之后还有一环重排**——检索是粗筛（bi-encoder），重排是精排（cross-encoder）。论文里没有这一环，是因为它把"取 top-k 直接喂 BART"当成了默认。
4. **每一环都要说得出"丢了什么"**——说不出来就等于没读懂那一环。

## 三、今天最值钱的一个负结果

```
「苹果手机多少钱一台？」 vs 「苹果多少钱一斤？」 = 0.8256   ← 全场最高
「RAG 通过检索外部文档来增强大模型的回答」 vs 「检索增强生成把知识放在索引里」 = 0.6475
「向量数据库用 ANN 加速搜索」 vs 「HNSW 用分层图实现快速近邻查询」 = 0.6556
```

三行连起来读：**同词不同义（0.8256）比不同词但语义相关（0.6556）更像**。

结论：稠密单向量在**同词不同义**上失效，因为整句压成一个向量、共同词占据同一方向、字面重合压过语义区分。这不是 bge-small 的 bug，是单向量表示的通病。

## 四、试过但没用的解法（避免以后重复踩）

| 想法 | 结论 |
|---|---|
| 把 512 维扩到 1024 维 | ❌ 不对症。维度是容量，不是区分能力；bge-large 变好主要靠数据与难负例 |
| 加语境改写法 | ⚠️ 部分有效：0.8256 → 0.7865（加"买手机/买水果"）→ 0.6656（去掉「苹果」） |
| 重排（cross-encoder） | ✅ 对症：让 query 与 doc 逐 token 交互，「手机」vs「一斤」的冲突能被识别 |
