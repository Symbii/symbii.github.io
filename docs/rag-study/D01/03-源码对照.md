关键输出：

| 项 | 结果 |
|---|---|
| 句数 × 维度 | 10 × 512，float32 |
| encode 输出模长 | min=max=1.000000（bge 自带 Normalize 模块，`normalize_embeddings=False` 也关不掉） |
| 手工余弦 vs 归一化点积 | 最大绝对差 2.384e-07（float32 舍入，即等价） |
| 反证：把 #1 放大 3 倍 | 点积 0.6475 变 1.9426，余弦仍是 0.6475 |
| 非对角相似度区间 | [0.189, 0.826] |
| 全场最高非对角 | #5 vs #6 = 0.8256（苹果对子） |
| 语义同类对照 | #0 vs #1 = 0.6475（RAG 两句） |

四条结论：

1. 归一化让内积等于余弦，条件是两者模长都为 1。点积会随模长漂移，所以工程上要么模型内建 Normalize（bge 就是），要么在入库/查询前显式除模长。
2. 相似度绝对值没有意义。0.19–0.83 这个区间只在同一个 query 内部排序时有含义，不能拿 0.8 当相关阈值，不同模型、不同语言、长短句都会让整体平移。
3. 同词歧义没有被拉开。苹果对子 0.8256 是全表最高分，比语义真正同类的 RAG 对子 0.6475 还高。用苹果手机多少钱去检索，Top-1 会命中苹果多少钱一斤，这是今天最值钱的负结果，它直接证明纯稠密检索不足，D04 的 BM25 与第 2 周的重排就是为了治这类错。
4. 底噪约 0.25–0.36。无关句之间也有 0.25 左右相似度，说明靠绝对阈值过滤不可靠；正确做法是 top-k 截断加重排，不是小于 0.5 就丢。

| # | 调用 | 文件:行 | 在做什么 |

查询用 `encode_queries`，入库用 `encode`，BGE/DPR 对 query 与 document 的编码方式不同（query 可能带指令前缀），混用会系统性偏低。`emb_mdl` 是 `LLMBundle`（`api/db/services/llm_service.py:228`）包装层，转发给具体 provider（`BuiltinEmbed` 257 到 `HuggingFaceEmbed` 1252）。`emb_mdl is None` 的分支（search.py:315）服务 chunk 管理/排序查询，不是语义检索。融合数学在 `query.py:170–178`：`cosine*vtweight + token_sim*tkweight`（默认 0.7 / 0.3）。

| 环 | 实现锚点 | 丢什么 |
|---|---|---|
| ①语料 | 上传 → minio | 没进来的、过期的、越权的 |
| ②解析 | `chunk()` 内部 parsers | 版面、表格行列、图里的字 |
| ③切分 | `naive.py:1123` | 跨块上下文、指代 |
| ④编码 | `embedding_model.py:225/1236` | 字面、词序 |

| ⑦重排 | `search.py:673` | 只在 64 条内、混词面权重 |
| ⑧生成 | `generator.py:168`、`search.py:431` | 预算截尾、有损压缩、引用错位 |

最薄的一环是 ③切分，一个 1000 行函数管所有格式，还有 ⑦重排，只做 64 条且混词面分。

### 6.4 附带记住的工程概念

task 切分：PDF 默认每 12 页一个 task（paper 22 页）；MinerU/PaddleOCR、`one`/`knowledge_graph`/`resume`、`toc_extraction` 是整文件 1 个；Excel 每 3000 行；其它 1 个。增量更新的 digest 等于配置加页范围加 `content_hash`，内容变就 digest 变，删旧 chunk（旧 task 的 `chunk_ids`）重建，内容没变就复用旧 task，粒度是任务级，不是 chunk 级。存储上 minio 放原文件加图片，docStore 放 chunk 文本加向量。KNN 是 K-Nearest Neighbors，向量库执行的是近似 KNN（ANN）。
